Introduction and methodology

One system per learner, growing across three levels

The diploma is a progression of engineering competence. P0 alone does not produce an employment-ready developer.

AI-first, code-first

Learners work with AI coding assistants from week one, while learning the concepts they need to evaluate, modify and debug what the AI generates.

Continuous engineering quality

Version control, automated tests, security checks, documentation, peer review and deployment are introduced progressively from the start.

Individual ownership

One curated reference-project library keeps complexity comparable, but every learner has a separate repository, data model, implementation and technical defense.

Acceptance definition per release

Each release keeps everything before it and builds on it

  1. MVPEnd of P0At least two real connected operations, UI → API → persistent database, deployed for demonstration.
  2. V1End of P1Keeps the MVP flows and adds two substantial linked workflows, better roles, data integrity, core tests and a deployed demo environment.
  3. V2End of P2Reliable deployment, automated tests, recoverable migrations, observability, documented performance and incident response, and one bounded automation.

V1 and V2 are educational releases. Neither is a claim of unrestricted production readiness.

V1 definition

A demonstrable, maintainable educational release. It keeps P0 features and adds approved linked workflows, role-based access, a realistic relational schema, reproducible setup, core automated tests and a deployed demo environment.

Handoff to P2

V1's architecture, technical debt, risks and release evidence become the baseline P2 starts from.

Integrity and collaboration

At least one peer review a week, one short team integration exercise a month, and individual project variations that make copying less effective.

P2 acceptance and daily operations

When V2 is accepted, and what instructors record every day

The final release preserves the P0 MVP and P1 V1 baseline, and shows:

  • Reliable deployment and automated test evidence
  • Access controls and recoverable data migrations
  • Observability, documented performance and incident response
  • One bounded automation improvement
  • Optional LLM integration only where feasible and safe, with a non-LLM alternative

Reassessment

Individual remediation that never takes time from the group

  1. 1Written gap analysis within two training daysIssued by the lead instructor for every failed gate.
  2. 2Personalized remediation planDelivered in protected coaching and review slots or documented onsite make-up sessions, never replacing core instruction owed to the group.
  3. 3Two reassessment attempts within 14 calendar daysThe learner may attend general lessons, but dependent milestones are not approved and the learner cannot advance a level.
  4. 4Program director decidesUnresolved cases after the second attempt.

Extra hours

Remediation hours are logged separately and never double-counted within the standard 420 hours.

Who runs the reviews

A teaching assistant manages parallel reviews so the lead instructor stays with the group.

Fair tests

No-AI tests cover only concepts already taught and practiced, and the instructor publishes a skill blueprint for each gate in advance.

AI-first and independent understanding

Every AI-assisted change goes through six steps

  1. Define the acceptance criterion
  2. Propose implementation steps
  3. Request bounded AI help
  4. Inspect code and dependencies
  5. Run the tests
  6. Document verification and commit
  • No secrets or real personal data in AI tools. Synthetic data and environment templates only
  • Verify that a package exists and check its licence before installing it
  • No-AI tests cover taught techniques only; a predeclared offline reference sheet may be allowed
  • Individual project variations: a role rule, a data edge case or a workflow condition
